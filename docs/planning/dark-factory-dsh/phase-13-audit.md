## 5. Top five gaps, ranked by risk to the product claim

**GAP-001 — The effect outbox is performed inline and never settled, so the durability claim is false as shipped.**
**The exact defect, having read both sides:** it is neither a double-dispatch leak nor "nothing ever launches". `engine.runUnit` (`engine.ts:705-721`) commits attempt + lease + reservation + `launch` effect in one transaction and launches nothing. `factory run` then _performs_ that effect itself — `cloneAttempt` (`run.ts:302`), `launchAttempt` (`run.ts:318`) — and **never marks the row applied**: at `c363900`/`4ab57bf` there is no `settleApplied`/`markEffectApplied` call anywhere in `apps/cli` or `packages/core` (`git grep markEffectApplied` → fake-store and tests only). So the launch happens exactly once, and the outbox is left permanently `pending` for every run: the row is a lie about state, `claimPendingEffects` (`store.ts:2277`) grows monotonically, and `recover` has nothing it can retry because it also refuses to redispatch (`engine.ts:1113`). The engine's comment at `:706-708` — "a crash after commit retries the launch instead of losing it" — therefore describes a path that does not exist; what a crash after commit actually produces is a `dispatched` unit, an open attempt, a pending effect, and a lease that `recover` closes by marking the attempt `ambiguous`.
**Smallest fix, in order:** (1) after `launchAttempt` resolves, call `store.markEffectApplied(effect.effectId, at)` on both the success **and** the `ATTEMPT_AMBIGUOUS` path (the worker ran; retrying would launch a second process), and give the environmental refusals a `retryable` state so the row is honest ("nothing started, the operator can fix this"); (2) change the engine comment at `:706-708` to describe what recovery actually does, or implement the retry in `recover` — those are different products and the code currently promises the second while delivering the first. **Do not** implement a scheduler-style `createDispatcher` drain: `run` is synchronous and knows exactly which effect it is performing, so the claim is an idempotency assert, not a queue.
**Status at v2:** still true at HEAD. A fix is in flight in the working tree (`apps/cli/src/effects.ts`, untracked, 9 KB, created 10:34 on 2026-11-01) whose header states the same diagnosis: "_until this module, nobody did: `run` launched inline and never marked the effect applied, so every run left a permanently `pending` row, `recover` had nothing to retry, and `status` reported an outbox leak the CLI itself created_". This audit claims no credit for it and has not reviewed it for correctness; when it lands, re-run `e2e/cli/default/07-seams.test.ts` and add the assertion the module makes possible — after a successful `run`, `claimPendingEffects(1000)` is empty. **And the `status` falsehood is being fixed in that same in-flight change**, by its author rather than by me: `apps/cli/src/render/status.ts:449-462` becomes `outboxHealth(ctx)`, which counts `pending`, separates `retrying` (attempts > 0) from a genuine backlog, keeps `dead: null` with a detail that names the unreadable count instead of implying zero, and drops the false "the store exposes no read-only outbox count". I verified that count is **truthful** by driving the module against a temp store (no repo files touched): after `enqueueEffect` → `{pending: 1, retrying: 0, dead: null}`, a second read identical (the read is side-effect-free), and after `settleApplied` → `{pending: 0}`. That is the number the Lead asked for: real, and it clears itself when settlement runs.
**Assertion to add when the settlement commit lands** (to `e2e/cli/default/07-seams.test.ts` and to this entry, so closure is checkable rather than announced): after a successful `factory run` of a dark unit, `openStore(...).claimPendingEffects(1000)` is **empty**; after a `run` whose adapter refused with an environmental code it is **non-empty with `attempts > 0`** (the `retrying` bucket). Written as a condition rather than a claim because `apps/cli/src/effects.ts` is still uncommitted at `06020fd`.

**Still unfixed at HEAD and independent of it:** `apps/cli/src/render/status.ts:451-462` tells the operator "_the store exposes no read-only outbox count_" and reports `state: 'unavailable'`, `pending: null`. That is false — `store.ts:2277` is a pure `SELECT ... WHERE state = 'pending'` with no write and no claim, and `apps/panel/src/status.ts:436` already calls it on a GET. The correction is to call the same read in `buildStatus` and set `state: 'ok'`, `pending: rows.length`, `detail: null` (keeping `retrying`/`dead` as `null` until the store filters by state); it should land **after** the settlement fix, or the operator's first `status` will truthfully report a permanent backlog that no command can clear.
