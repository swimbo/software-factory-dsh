## 2. Amendments, by affected section of `architecture.md`

Each amendment is ordered to match the document. The quoted line is the **current** text; the change is what to replace it with; the rationale is why the debate forced it; the evidence is what carries it.

### A1 — `## 1. Design premise` ([`architecture.md:8`](architecture.md#L8))

**Change.** After the three laws, add a fourth inherited invariant, in the prior factory's own words:

> **I4 (inherited) — The wall is a quality gate, not a security boundary.** A dark lane terminates in the wall, and lit units still receive verdicts, so the wall is _security-critical in effect_ while being _behavioural-only in mechanism_. It does not, and must not be claimed to, prevent a spec-satisfying backdoor. Security is carried by the capability set (§2.2, §A5.2), not by the verdict.

And extend L3's symmetry with one sentence:

> L3 applies in both directions: a missing measurement is `unknown`, and an **infrastructure error is not a defect** — a scenario that errors on the harness must never be aggregated as a failed scenario (§A4.7).

**Rationale.** The inherited invariant is the only thing standing between "the wall passed" and "the change is safe", and the current §7 lists the wall inside the trusted zone ([`architecture.md:217`](architecture.md#L217)) without the disclaimer. A reviewer reading §7 and §9 together currently concludes the wall _is_ the security boundary. Separately, QD found that `ScenarioResult.outcome='error'` counts in the denominator of `holdout_pass_rate` ([`data-map.md:895`](data-map.md#L895)), so an infra outage writes a permanent Δ sample and silently narrows the dark lane — `unknown` being aggregated as a defect, which is L3 read backwards.

**Evidence.** [`findings.md:108`](findings.md#L108) records invariant #4 verbatim; [`existing-state.md:225-226`](research/existing-state.md#L225-L226) is the prior repo's own disclaimer. On the second point: [`data-map.md:349`](data-map.md#L349) (`outcome` enum includes `error`), [`data-map.md:895`](data-map.md#L895) (`scenarios meeting 2-of-3 / total`), [`data-map.md:391`](data-map.md#L391) (a `DeltaSample` is written when both rates are known) — three schema facts that compose into the bug. On behavioural-only walls and spec-satisfying backdoors: arXiv 2605.31042 reports **95.5 % ASR** for multi-step trojans where single-turn ASR is near zero ([arxiv.org/abs/2605.31042](https://arxiv.org/abs/2605.31042), submitted 2026-05-29; **inference** for DSH/DeepSeek transfer — the measurement is on GPT-5.4 in an OpenClaw-style workspace).

### A2 — `### 2.1 Control plane` ([`architecture.md:80`](architecture.md#L80))

**A2.1 Two-phase effects; resolution by observation, never by re-invocation.** Replace the last sentence of the idempotency bullet ([`architecture.md:86`](architecture.md#L86)):

> ~~Re-running an effect with the same key is a no-op that returns the stored result.~~
>
> **Every effect is two rows in one table: an `intent` row committed with the command (carrying the observation recipe — container name, worktree path, pid/pgid, session id), and an `outcome` row committed after the sink is observed. Re-running an effect whose outcome is unknown is forbidden. `in_flight` at startup is resolved only by probing the sink under the effect key; it is never resolved by a timer, a backoff, or a re-dispatch. An effect that cannot be resolved within its settlement budget becomes `dead` and the unit becomes `ambiguous`.** `outcome` is the only channel from which a replay may return a stored value.

**Rationale.** `in_flight` appears **exactly once** in the entire plan set — as the `CHECK` constraint at [`data-map.md:488`](data-map.md#L488). The only drain query selects `state='pending'` ([`data-map.md:815`](data-map.md#L815)), and recovery only marks _attempts_ ambiguous ([`architecture.md:87`](architecture.md#L87)). A crash after the side effect and before `done` therefore either redispaches (duplicate `docker run` / `git worktree add` / `mintToken`, falsifying §8's "zero duplicate side effects") or orphans the row forever. The prior factory had `reserve() → {new, unknown, completed}` ([`existing-state.md:51`](research/existing-state.md#L51)); the new model regressed it. §8's idempotency NFR ([`architecture.md:224`](architecture.md#L224)) is unestablishable until this is fixed, and it is a **9a schema property**, which is why it cannot wait.

**Evidence.** [`data-map.md:488`](data-map.md#L488), [`data-map.md:815`](data-map.md#L815), [`architecture.md:87`](architecture.md#L87), [`existing-state.md:51`](research/existing-state.md#L51). The 9a crash test as written is the _easy_ window: "open store, enqueue, **abandon without `drain`**, reopen" ([`phase-9a-plan.md:26`](phase-9a-plan.md#L26)) — before dispatch, by construction.

**A2.2 Effect ordering must be causal, not per-kind.** Amend the outbox bullet in §3/C3 ([`architecture.md:153`](architecture.md#L153)): ordering groups are `kind + ':' + unit_id` ([`data-map.md:485`](data-map.md#L485)), so `dispatch_attempt`, `collect_receipt`, `verify_unit`, `kill_attempt` and `settle_spend` for one unit are mutually unordered. `runUnit` already fails fast on `LANE_NOT_DARK` ([`architecture.md:170`](architecture.md#L170)) while the lane decision is asynchronous; `kill_attempt` can be applied before a queued dispatch starts a container with a live token. **Change:** lifecycle-critical kinds share one ordering key per unit, and order comes from data dependency carried in the payload (the token id, the prior result), not from the kind name.

**A2.3 Time enters in the command.** "A pure function of `(state, command)`" ([`architecture.md:84`](architecture.md#L84)) is false the moment a handler reads a clock. The prior repo's `Date.now()` lease is already flagged "Retire" ([`existing-state.md:294`](research/existing-state.md#L294)). **Change:** every timestamp is a command field; lease expiry is an `expireLeases(tick)` command, never a timer callback.

**A2.4 Reducers are versioned.** §8.4 detects corruption by replaying from `seq 1` **through the current handlers** ([`data-map.md:979`](data-map.md#L979)); any handler refactor after real data exists changes the aggregate hash → quarantine → "never reset" → the factory stops. **Change:** `reducer_version` is part of the aggregate hash manifest, and replay-verify is scoped to a version with a recorded migration step.

**A2.5 Fencing must be a parameter, not a law.** I8 rejects stale-holder writes ([`data-map.md:837`](data-map.md#L837)), but **no operation in §4's table carries a fencing token** ([`architecture.md:167-176`](architecture.md#L167-L176)) and `recordReceipt` is adapter-supplied in-process. **Change:** `fence` is a required parameter on every mutating command and the store rejects a stale one. A law no caller can obey is not enforced; it is documented.

**A2.6 The spend ceiling is demoted.** Replace the watchdog clause ([`architecture.md:88`](architecture.md#L88)):

> ~~per-attempt token ceiling from the session log's usage projection~~
>
> **per-attempt token/turn/wall-clock ceilings are enforced by the credential proxy from its own metered counters (§A9.1). The session log's usage projection is an _audit_ signal: it is recorded, compared against the proxy's count, and a divergence greater than the tolerance fails the attempt as `unknown`. It is never the ceiling.**

**Rationale.** The ceiling is computed from a log written inside the worker's own `DSH_HOME` ([`architecture.md:107`](architecture.md#L107)), stored as "checksummed zstd frames" whose checksum is **XXH64 with a seed of zero — unkeyed, therefore recomputable by anyone with write access** ([`research/dsh-architecture.md:342-346`](research/dsh-architecture.md#L342), [RFC 8878 §3.1.1](https://www.rfc-editor.org/rfc/rfc8878.html)). A worker that calls the proxy with `curl` spends money the log never sees; a worker that rewrites its own container-local log under-reports with a valid checksum. Under **L2** ([`architecture.md:15`](architecture.md#L15)) a control derived from a channel the controlled party writes is not a control. This is also an inherited-invariant violation: #2 says budget is a _best-effort estimate_ ([`findings.md:106`](findings.md#L106)) — the plan promoted an estimate to an authority without moving the measurement.

### A3 — `### 2.2 Execution plane` ([`architecture.md:90`](architecture.md#L90))

**A3.1 The port gains the method its law requires.** Replace the interface ([`architecture.md:95-100`](architecture.md#L95-L100)):

```ts
interface Executor {
  start(attempt: AttemptSpec): Promise<AttemptHandle>; // adopt-or-start, keyed by container label
  adopt(attemptId: string): Promise<AttemptHandle | null>; // reconstruct from AttemptIdentity; null if the world disagrees
  observe(handle: AttemptHandle): Promise<Progress>; // read-only, never mutates work
  terminate(handle: AttemptHandle, why: string): Promise<void>;
  collect(handle: AttemptHandle): Promise<WorkerReceipt>;
}
```

`AttemptHandle` must be **reconstructible from `AttemptIdentity` alone** — that is the whole point of freezing pid/pgid, container name, session id, `dsh_home`, `patch_hash` ([`data-map.md:227-241`](data-map.md#L227-L241)). `start`'s comment "idempotent on attempt.id" is currently a promise the port cannot keep.

**Rationale.** §2.1 says the engine "re-observes them under their original identity" ([`architecture.md:87`](architecture.md#L87)); the port holds only an in-memory handle, and **`adopt(` and `attach(` appear zero times in the plan set**. After a crash the engine holds no handle, so `observe`/`collect` are uncallable. The reconciliation law is the plan's entire resilience story and it has no interface.

**Evidence.** [`architecture.md:95-100`](architecture.md#L95-L100), [`architecture.md:87`](architecture.md#L87), [`data-map.md:227-241`](data-map.md#L227-L241); exhaustive grep of `docs/planning/dark-factory-dsh/*.md` for `adopt(`/`attach(` returns 0.

**A3.2 The worktree must be a self-contained clone at the identical path.** Replace step 1 ([`architecture.md:105`](architecture.md#L105)):

> ~~`git worktree add --detach <attemptDir> <baseRevision>` from a pristine clone (never the operator's working tree), inside `~/.factory/work/`.~~
>
> **`git clone --no-hardlinks --shared-from <pristine> <attemptDir>` then `git checkout --detach <baseRevision>`, so `.git` is a directory inside `<attemptDir>`; `<attemptDir>` is bind-mounted at the _same absolute path_ inside the container, so the cwd recorded in `AttemptIdentity.worktree_path` matches in both worlds.**

**Rationale.** A linked worktree's `.git` is a **file** containing an absolute host path (`gitdir: /private/tmp/…/repos/demo.git/worktrees/11`) — verified locally on this host with git 2.50.1, both plain and `--relative-paths` (SA). With "one bind mount (`attemptDir`)" ([`phase-9b-plan.md:24`](phase-9b-plan.md#L24), [`architecture.md:107`](architecture.md#L107)), every `git` invocation inside the worker container resolves a path that does not exist. **Inference:** unless the clone is self-contained _and_ the path is identical, 9b's container cannot run `git status`, and the receipt capture at [`architecture.md:109`](architecture.md#L109) fails at step one. The identical path is not cosmetic: `--session-id` adoption refuses when cwd differs ([`research/dsh-architecture.md:260`](research/dsh-architecture.md#L260)), so attempt-path stability _is_ the reconciliation mechanism.

**Cost to record.** One clone per attempt. At 20 units/day × up to 3 attempts and a 7-day post-verdict retention ([`data-map.md:962`](data-map.md#L962)), a 1 GB repo is ≈420 GB. **Inference:** `--shared`/hardlink clones would put the worker's object store in the pristine mirror's inodes, reintroducing a shared writable object store; not worth the disk.

**A3.3 Network and egress are a topology, not an intention.** Replace the egress clause of step 3 ([`architecture.md:107`](architecture.md#L107)) and the §7 bullet ([`architecture.md:215`](architecture.md#L215)):

> **The worker runs on a dedicated `docker network create --internal` network with exactly two members: the worker and the proxy. The proxy is dual-homed (internal + egress) and is the only member with a route; it is reached by container name. `host.docker.internal`, public IPv4/IPv6 literals, DNS, and the metadata endpoint are unreachable from the worker, and the negative-egress test asserts each of those destinations is closed.**

**Rationale — this is the debate's hardest external fact.** On this host (Docker 29.8.2, macOS 26.4 arm64, [`phased-plan.md`](phased-plan.md) environment snapshot), a container on the **default bridge with no flags** reached `host.docker.internal:5432`, `:11434`, **`:65107` (the operator's DSH GUI)**, `1.1.1.1:443`, and `example.com:443`. The plan asserts "no route except the credential proxy" ([`architecture.md:215`](architecture.md#L215)); by default the worker has the whole internet and the operator's loopback. The named mechanism — `--network` "restricted to the credential-proxy host" ([`phase-9b-plan.md:24`](phase-9b-plan.md#L24)) — **is not a Docker operation**. The enforceable shape was then verified: `--internal` closed every host listener and all public egress, and a dual-homed container remained reachable _by name_.

**A3.4 `DSH_HOME` is a per-attempt volume (resolution of a self-contradiction).** Step 3 sets `DSH_HOME=~/.factory/dsh-home/worker` "per trust domain" and simultaneously "no host mounts except the attempt directory" ([`architecture.md:107`](architecture.md#L107)) while [`phase-9b-plan.md:24`](phase-9b-plan.md#L24) permits exactly one bind mount. Both readings fail: container-local loses the session log with the container (so `collect()` cannot produce `session_tree[]`, and the token ceiling has nothing to read); a bind mount of the parent puts `~/.factory/holdout/` one `..` from the mount. **Change:** `DSH_HOME` is a **per-attempt named volume** (`factory-home-<unitId>-<attemptNo>`), mounted at a container-internal path, seeded read-only from a template, read out by the adapter with `docker exec`/`docker cp`, destroyed after receipt capture and offload.

**Rationale.** This also closes a cross-attempt contamination channel nobody else flagged: one `dsh_home` serves **all** worker attempts ([`data-map.md:241`](data-map.md#L241)) and `$DSH_HOME/cordis.patch.yml` applies to every profile ([`findings.md:118`](findings.md#L118)) — attempt N could configure attempt N+1. The NDJSON event set has no `usage` event ([`research/dsh-architecture.md:252-265`](research/dsh-architecture.md#L252-L265)), so the session log is the _only_ source for the audit comparison in §A2.6; it must survive.

**A3.5 Receipt capture must see ignored files.** Amend step 5 ([`architecture.md:109`](architecture.md#L109)): capture `git status --porcelain **--ignored=matching**` and `git ls-files --others --ignored --exclude-standard`, and treat **any write to a gitignored path** as either `receipt_unfaithful` or `lit`. Verified on this host: `git status --porcelain` hides `!! ignored.txt`; `--ignored=matching` shows it. A worker can write a `.env`, a fixture, or a token to an ignored path and the diff, the untracked list, the receipt and the escape audit all miss it. This is not hypothetical for credential flow: the worker holds a proxy token.

**A3.6 `commands[]` needs a named producer and a truncation rule.** [`data-map.md:283-298`](data-map.md#L283-L298) defines `CommandRecord` but no component produces it. DSH's `--json` caps every string at 8 KiB with a `truncated` flag ([`research/dsh-architecture.md:261`](research/dsh-architecture.md#L261)); a **truncated** command must fail closed rather than enter the forensic record. Since CP-8 demotes `commands[]` out of the decision path, the residual risk is audit-only — but the producer and the truncation rule still have to exist.

### A4 — `### 2.3 Verification plane` ([`architecture.md:112`](architecture.md#L112))

This is where the debate changed the most. Six amendments, of which the sixth is the artifact's central promise.

**A4.1 Replay executes the wall's entrypoint over a committed tuple, not worker argv.** Replace the deterministic re-execution bullet ([`architecture.md:116`](architecture.md#L116)):

> ~~check out the receipt's diff onto a clean base, replay the receipt's `commands[]` in a fresh container, and compare exit codes and full-suite output.~~
>
> **The receipt commits to `{argv[], cwd, baseRevision, envDigest}`. The wall applies the candidate source to a clean base, checks out the base test root (`git checkout <base> -- <testRoot>`), and replays _its own pinned entrypoint_ over that tuple. The worker supplies argv only; it never supplies the entrypoint. Faithfulness is then a comparison of a machine-readable suite summary (counts, failed ids, exit code) — never of free-text logs, which contain timings and temp paths and therefore false-fail on faithful receipts. `commands[]` is retained as forensic evidence and is not replayed.**

**Rationale.** Two failures compose. `receipt.commands[]` is attacker-authored data executed **verbatim** in "a fresh container" ([`phase-9c-plan.md:22`](phase-9c-plan.md#L22)), i.e. untrusted argv at wall privilege — and the wall holds the holdout and the signing key. Separately, "compare exit codes and full-suite output" compares text with no normalisation spec: either the wall flags every faithful receipt (a false-fail machine that fails closed to zero throughput) or it silently greps. A machine-readable summary is the only comparison that survives L1.

**A4.2 Path fence and the non-empty-diff invariant.** Add to the same bullet:

> **A diff outside the declared touch-paths ⇒ `receipt_unfaithful`, before replay. `diff == ∅ ∧ status ≠ ∅ ⇒ receipt_unfaithful`. `diff == ∅ ∧ status == ∅ ⇒ no_change` — never `pass`. Any diff touching the test root, the dependency manifest, the lockfile, a test-runner config, a CI script, or `.git/hooks` ⇒ `lit`.**

**Rationale.** `git diff <base>...HEAD` ([`architecture.md:109`](architecture.md#L109)) is **empty if the agent never commits** while the work sits in `git status --porcelain`; the wall then replays an empty patch onto a clean base and reports "replays faithfully". No invariant ties `diff` to `porcelain`, and touch-paths are currently used only to _score_ reversibility ([`architecture.md:130`](architecture.md#L130)). The prior factory had `allowed_paths` ([`existing-state.md:250`](research/existing-state.md#L250)); the new plan dropped it. And the manifest case is the oracle hole: the wall's pinned runner still installs from the **candidate's** `package.json`/lockfile, so a `postinstall` is executable code in the oracle (B13).

**A4.3 Holdout exposure needs a budget, not just a retirement column.** Add after the holdout bullet:

> **`verifyUnit` is capped per unit per `policyVersion`; a scenario that fails once for a unit is retired for that unit (fail-once); the scenario set rotates ≥20 % every 10 verdicts; and at most 3 certification attempts per class per `policyVersion` are allowed before human re-validation. Exceeding any cap ⇒ `unknown`, not a retry.**

**Rationale.** `HoldoutScenario.retired_at` exists ([`data-map.md:369`](data-map.md#L369)) but no policy consumes it, and `Mandate.strength.max_attempts` exists with no value. Reusing a holdout adaptively is precisely what Thresholdout exists to bound — "reusing a holdout set adaptively multiple times can easily lead to overfitting to the holdout set itself" ([arXiv 1506.02629](https://arxiv.org/abs/1506.02629), Dwork et al., 2015; Science 2015 companion). An adversary who may spend unlimited attempts against a fixed holdout has converted the gate into a search problem.

**A4.4 The candidate-execution substrate is named (CP-6).** Amend the scenario bullet ([`architecture.md:117`](architecture.md#L117)) and [`phase-9c-plan.md:23`](phase-9c-plan.md#L23):

> **Each scenario run executes the candidate in a fresh container from the same digest-pinned `factory-env` image: non-root, read-only root filesystem, `--internal` network with no egress, **no mount of `~/.factory`**, no holdout store, no key material. The scenario driver runs _outside_ that container, holds the expected values, and asserts over HTTP/CLI/data on a one-way channel. No expectation is ever serialised into the candidate's process, filesystem, or environment.**

**Rationale.** [`phase-9c-plan.md:23`](phase-9c-plan.md#L23) says "triple-run each scenario against an ephemeral deployment" and names no uid, mounts or network. A CLI/assertion driver that spawns the candidate as a child process puts the candidate's `Makefile`, `conftest.py` or `package.json` scripts **in the process holding the holdout and the signing key** — the exact class in [`pain-points.md:121`](research/pain-points.md#L121) (Cursor `.claude` hook → unsandboxed execution). The plan's proof that the wall is separate was E2E-46, which asserts a **cwd string and a `DSH_HOME` string** ([`e2e-tests.md:179`](e2e-tests.md#L179)); a path assertion is not a trust-boundary assertion.

**A4.5 The holdout-blindness test moves to the evaluator layer.** Replace "a worktree cannot read the holdout store" ([`architecture.md:121`](architecture.md#L121)) with: _the candidate cannot read the holdout; the driver can_. The worker-side container test is necessary but not sufficient — the second place untrusted code runs is the scenario container, and it is untested.

**A4.6 The acceptance rule becomes an operating characteristic (CP-1).** Replace "Triple-run, 2-of-3 per scenario, ≥90 % aggregate" ([`architecture.md:117`](architecture.md#L117)):

> **Acceptance is governed by a pre-registered operating characteristic over a stated `(m, k, quorum)` per scenario class. `m`, `k`, and the quorum are fields of `PolicyVersion`; α (probability of certifying a candidate whose true per-run pass rate is 0.85) and β (probability of failing a candidate at 0.97) are published in §9 and recomputed by a test whenever the policy changes. The 90 % point-estimate aggregate is retired as a certification authority.**

**Rationale — the arithmetic.** `q = p²(3−2p)` is the per-scenario pass probability under 2-of-3:

| Rule                                                                   | α at p=0.85 | β at p=0.97 | Candidate runs / verdict |
| ---------------------------------------------------------------------- | ----------- | ----------- | ------------------------ |
| m=6, k=6 — **the design point** ([`data-map.md:27`](data-map.md#L27))  | **0.687**   | 0.016       | 18                       |
| m=9, k=9 — the shipped fixture ([`e2e-tests.md:66`](e2e-tests.md#L66)) | 0.569       | 0.024       | 27                       |
| m=20, k=18 — **"90 %" at m=20**                                        | **0.882**   | ~0          | 60                       |
| m=20, k=20 — unanimity                                                 | 0.286       | 0.052       | 60                       |
| m=40, k=40                                                             | 0.081       | 0.101       | 120                      |
| m=48, k=48                                                             | 0.049       | 0.119       | 144                      |
| m=48, k=44 — **"90 %" at m=48**                                        | **0.836**   | ~0          | 144                      |
| 180 run-level trials, k=162                                            | 0.038       | ~0          | 180                      |

Two facts fall out, and they are the reason CP-1 is unanimous. **(i)** At every scenario count the plan set actually specifies — 5 ([`existing-state.md:216`](research/existing-state.md#L216)), 6 ([`data-map.md:27`](data-map.md#L27)), 9 ([`e2e-tests.md:66`](e2e-tests.md#L66)) — 4/5 = 0.80, 5/6 = 0.833 and 8/9 = 0.889 are all below 0.90, so "≥90 % aggregate" **is unanimity**: a gate wearing a percentage. **(ii)** At `m ≥ 10` the rule tolerates failures (`k = ceil(0.9m)`), and α **jumps and then plateaus**: 0.880 at m=10 (one failure allowed), 0.882 at m=20, 0.90 at m=30, 0.836 at m=48. "Raise `m`" is therefore **not a fix** — for m ≥ 10 the gate certifies a candidate that fails one run in seven about **84–90 % of the time**, which is not a threshold but a lottery.

> **Correction to the moderator's brief, recorded:** the post-round brief describes this as _"non-monotonic in m; consumer risk rises as scenarios are added."_ The conclusion holds but the framing overstates. The precise behaviour is a **step function with a plateau**: α is `q^m` (falling) while `k = m`, then jumps at each increment of `k` and sits in a 0.82–0.91 band for all `m ≥ 10`. I use the plateau formulation because a reader who checks `m=48 → 0.836` against `m=20 → 0.882` would otherwise find a counterexample to "rises".

**A4.7 Δ: one producer, one error rule, one bootstrap rule (CP-11).** Replace the Δ bullet ([`architecture.md:118`](architecture.md#L118)):

> **`Δ = visible_pass_rate − holdout_pass_rate`, where _both_ rates are measured by the wall: `visible_pass_rate` over the holdout's copy of the visible-suite base, `holdout_pass_rate` over the frozen scenario set. Any scenario run whose outcome is `error` ⇒ `verdict = 'unknown'`, **no** `DeltaSample`, and `errored` surfaced by `factory status`; errored runs are excluded from the denominator, never counted as failures. Δ undefined, or `n_samples < min_samples` for the class ⇒ the _class_ is not certifiable; the unit may still verify, but every promotion in that class carries a human signature; one human-signed `bootstrap` reason code is allowed per class per `policyVersion`.**

**Rationale.** `visible_pass_rate` appears in the plan set **only** as a schema field ([`data-map.md:328`](data-map.md#L328)) and inside the Δ formula — nothing states whether it comes from the re-executed run or is parsed from the worker's `suite_output`. If the latter, Δ's left operand is worker-controlled and the plan violates its own L1. The error rule is a direct L3 violation (see §A1). The bootstrap rule closes a cold-start hole under L3 that would otherwise make **the first unit of every class permanently uncertifiable** — an unstated rule that would have surfaced as a mystery stall in week one.

**A4.8 The self-adversarial suite gets a criterion, not a corpus size (CP-1, G2).** Replace "a sabotage corpus" ([`architecture.md:121`](architecture.md#L121)):

> **The self-adversarial suite is a measured instrument, versioned with the `WallRevision`: ≥ 29 known-good patches (so `0.9^29 = 0.047` bounds the false-fail rate at 10 % with a one-sided 95 % bound), ≥ 30 mutation-derived defects that pass the visible suite (30/30 gives a one-sided 95 % lower bound on rejection of 0.905), verdict-flip rate ≤ 5 % over 10 repeated evaluations of the same receipt, and every scenario must be tripped by ≥ 1 corpus defect or be retired. `@docker` tests are **blocking** for the security rows; a skipped Docker suite leaves those rows `unknown`, never `pass`.**

**Rationale.** [`phase-9c-plan.md:26`](phase-9c-plan.md#L26) asks for ≥ 3 sabotage fixtures and **no rejection-rate or false-fail threshold**, and the meta-test at [`user-stories.md:159`](user-stories.md#L159) is the only mutation test of the wall. The corpus arithmetic is exactly the standard the plan already applies to a _less_ important component: [`phase-9d-plan.md:56`](phase-9d-plan.md#L56) demands "≥ 15 normalised commands … zero false-negatives on the destructive set" for the destructive classifier. The wall, which decides whether a human ever reads a diff, had no such standard. Under L3 an unmeasured suite is `unknown`.

**A4.9 The evaluator key leaves `~/.factory` (CP-13).** Covered in §A10.2. The verdict-signing key must not sit inside `~/.factory/holdout/`, which is the directory whose unreadability _is_ the security NFR: one containment failure then yields blindness **and** forgery.

### A8 — `## 5. Data ownership` ([`architecture.md:183`](architecture.md#L183))

**Change.** Replace the `Verdict` row ([`architecture.md:191`](architecture.md#L191)):

> | `Verdict`, `HoldoutScenario`, `WallRevision`, `DeltaSample` | C7 wall | The wall emits a **signed verdict artifact**; the core stores a `VerdictRef` = `{verdictId, contentHash, signature, signerKeyId, wallRevision, policyVersion}` and **never accepts an unsigned row**. The scenario bodies, expected values and Δ history never enter the core database. |

And qualify the "only writer" claim ([`architecture.md:82`](architecture.md#L82)):

> The only writer of `factory.db`. The wall's own store is written only by the wall; the join between them is `sha256(unitId, verdictId, contentHash)` and **no transaction spans the two stores**.

**Rationale.** Three statements cannot all be true: core is "the only writer of authoritative state" ([:82](architecture.md#L82)), the wall owns `Verdict`/`DeltaSample`/`HoldoutScenario` ([:191](architecture.md#L191)), and the wall runs as a second process ([:210](architecture.md#L210)) under `data-map.md:14`'s "one process, one writer". The promotion key `sha256(unitId, verdictId)` ([`architecture.md:174`](architecture.md#L174)) then spans two stores with no shared transaction — an implicit distributed transaction. **Two writers to one SQLite file** is also a corruption vector, not just lock contention: the WAL-reset bug affects databases with **two or more connections** on the same file, fixed in SQLite 3.51.3 ([sqlite.org/wal.html §11.1](https://www.sqlite.org/wal.html)). The host bundle is 3.51.3, so it is patched _if_ Node's bundled build matches — unverified.

**Which placement wins depends entirely on §R2.** On one uid, the split is two files the same process can open: strictly more operational surface for no security gain, and `factory audit` loses its single timeline. The split's only genuine advantage is against a compromised **core** (a wall-owned store the core uid cannot write means a core compromise cannot fabricate a verdict); against a compromised **wall** both designs are equal, because the wall holds the signing key either way. So the split is worth its cost **only if the second uid is real**.

## 6. Residual / needs human decision

Four items. Two are HIGH and block a phase gate; two are scope choices with a written default. Each names the options, the recommended default, and the evidence that would change the answer.

### R1 — The certification operating point (blocks 9c acceptance) · HIGH

**Why it cannot be decided from evidence.** The two targets are jointly infeasible under per-scenario 2-of-3 unanimity: α ≤ 0.05 needs `m ≥ 47.8`; β ≤ 0.10 needs `m ≤ 39.8` (computed from `q(0.97) = 0.997354` and `q(0.85) = 0.93925`). One target must move. That is a value choice about which error is worse — a certified-bad unit, or a false-fail that consumes operator attention — and no amount of measurement resolves it.

| Option                                                      | α at 0.85 | β at 0.97 | Runs / verdict | Runs/day at 20 units |
| ----------------------------------------------------------- | --------- | --------- | -------------- | -------------------- |
| **(a)** m=48, k=48, 2-of-3                                  | 0.049     | 0.119     | 144            | 2,880                |
| **(b)** m=40, k=40, 2-of-3                                  | 0.082     | 0.101     | 120            | 2,400                |
| **(c)** 180 run-level trials, k=162, no per-scenario quorum | 0.038     | ~0        | 180            | 3,600                |
| **(d)** keep m=6 and publish α=0.687                        | 0.687     | 0.016     | 18             | 360                  |

**Recommended default: (b)**, re-ratified against Block C-4's measured service time. Rationale: it is the only option that meets a 10 % false-fail budget _and_ keeps per-scenario quorum, at 120 runs rather than 144; (c) is statistically cleaner but abandons the quorum and costs 50 % more compute; (d) is not defensible at any `m`.

**Blocking evidence to collect first:** wall p50/p95 service time per run and per verdict on this host (§3 C-4), and the intra-cluster correlation ρ of the three runs of a scenario. **Inference, unflagged by anyone in Round 1:** the three runs share code and environment, so positive ρ inflates variance by a design effect of roughly `1 + 2ρ` and makes every α in the table optimistic. Until ρ is measured, publish the OC as an _upper bound on power_, not a guarantee.

**Cost of being wrong:** a reversal after 9c is a corpus rebuild (`m` scenarios × 3, per class) plus a re-run of the entire calibration; a reversal after 9a is cheap by comparison — which is why 9a is not blocked on this.

### R2 — Verdict store placement + second uid + wall topology (blocks 9a schema) · HIGH

**The decision rule.** The split's only advantage is against a compromised **core**. That advantage exists **only if the second uid is real**. On one uid, a wall-owned store is a second file the same process can open: strictly more operational surface, no security gain, and `factory audit` loses its single timeline.

**Note the coupling:** CP-13's key placement says "under the second uid **if** §R2 admits one". Under (a), the key still leaves `~/.factory` (that part is not conditional) but the uid clause is inert. Resolve R1 and R2 before 9a's schema freeze; everything else in this document is an edit with an agreed owner.

### R3 — Proxy metering semantics (blocks nothing; blocks the _proof_ of the cost NFR) · MEDIUM

CP-14 resolves **who** holds spend authority (the proxy). What it counts is open: bytes vs tokens vs provider-reported usage; where the signed usage record lands (a proxy log, a `spend_entry` column, both); and how a proxy count that disagrees with Bifrost's invoice is reconciled. **Recommended default:** count requests, request-body bytes, and **provider-reported completion tokens** (the only figure Bifrost can invoice against); emit one signed record per attempt; reconcile in `factory status` with an explicit tolerance; a divergence beyond tolerance ⇒ `unknown`, never a silent average.

**Why it is not LOW:** [`architecture.md:228`](architecture.md#L228) already says the per-unit envelope is "$2 estimated" with `unknown` propagation — consistent with inherited invariant #2's "best-effort estimate, not a charge cap" ([`findings.md:106`](findings.md#L106)). Turning an estimate into a cap requires a measurement the plan does not have; DSH's own token meter is explicitly "not billing-grade" ([`research/dsh-architecture.md:438-447`](research/dsh-architecture.md#L438-L447)).

### R4 — Off-host anchor scope · MEDIUM/LOW

CP-10 adopts the **honest statement** ("coordinated rollback of ledger + anchor is undetectable in v1") plus a local tamper-evident watermark hash-chained into the next human-signed promotion. The alternative — a real off-host WORM/remote anchor — is the only thing that detects the attack, and it needs a named substrate (second disk, remote git, WORM bucket). **Recommended default:** ship the statement in v1; name the v1.1 target. **Cost of the deferral:** the plan must not claim a mitigation it does not have, and today it does ([`data-map.md:986`](data-map.md#L986)).

## 8. What this plan does not establish

Stated plainly, because the artifact's own law requires it:

1. **It does not establish that a dark lane is safe.** It establishes a _measured_ gate with a published error rate, an _adversarially calibrated_ instrument, and a set of controls that no longer trust the party they restrict. Whether the wall catches a spec-satisfying backdoor is `unknown` and stays `unknown`; the wall is a quality gate, not a security boundary (§A1).
2. **It does not establish the security NFR.** Two of its three clauses (no holdout, no key) become testable with §A3 and §A4.4; the third (no operator home) becomes testable with §A3.3. Until Block B runs with `@docker` blocking, the row is `unknown`.
3. **It does not establish crash-safety.** It makes crash-safety _expressible_ (§A2.1) and _testable_ (Block A). The NFR's truth value is `unknown` until A-1 passes.
4. **It does not resolve the two value choices.** §R1 and §R2 are the operator's, and both must be signed before 9a freezes the schema.
5. **It does not fix the plan set.** §5 lists the twelve edits; until they land, the plan set contains contradictions that will be implemented as bugs with two test suites each defending its own reading.
